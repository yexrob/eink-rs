# Markdown 流式渲染：正式实施

- 日期：2026-10-22
- 状态：实施中
- 提交：无
- Brief：[markdown-stream](briefs/markdown-stream.md)、[markdown-stream-gaps](briefs/markdown-stream-gaps.md)

## 背景

[016](016-markdown-stream.md) 合入了初稿和 demo。它的结果里列了三点：尾部的长度决定每帧开销；高亮第一次编译语法时卡帧；时钟在整个回答期间运行。用户认可，并要求「做完记得压测大数据量的场景」。

Claude 用 scratchpad 里的基准补测了更大的尾部。条件同 016：release 构建，每次喂 16 字节，重渲染尾部。

| 尾部 | p50 / p90 |
|---|---|
| 300 行代码块，无高亮 | 4.8 / 5.9 ms |
| 300 行代码块，高亮 | 12.9 / 15.6 ms |
| 300 项列表 | 7.5 / 10.6 ms |
| 300 行表格 | 11.0 / 14.2 ms |
| 20 KB 段落 | 10.3 / 14.1 ms |
| 内容没变的帧，300 行代码作尾部 | 1.1 ms，高亮 1.5 ms |

另外两点：

- ink-rs 的非全屏模式在动态区超过屏高时从顶部裁掉。尾部比屏幕高时，上面的部分在流式期间看不见。
- 初稿的模型每完成一行就重新解析整个未完的块，匀速揭示每次 tick 数一遍积压的全部字素。

用户说「对一下方案吧」。Claude 提了方案，问了三个问题：

- **列表的定稿粒度**，「按项定稿」或「整块定稿」：用户选「按项定稿」。
- **表格**，「整表定稿」或「冻结列宽逐行定稿」：用户选「整表定稿」。
- **谁来写**：Claude 提的是并行派两个 Codex 写模型和高亮线程，第二步派一个写 hook 和 demo。用户答「一次性写，你给方案 codex开工」。

## 决策

用户定：

- 列表按顶层的项定稿（「按项定稿」）。
- 表格整表定稿（「整表定稿」）。300 行表格每帧约 11ms，记为已知限制。
- Claude 出方案，一个 Codex 一次写完（「一次性写，你给方案 codex开工」）。

以下由 Claude 按用户的授权（「你给方案」）定。

### 1. 定稿的单位

`MarkdownStream` 输出 `MarkdownPiece`，取代整块的源码。一段输出时即是定稿：之后到达的文本不改变它的渲染。初稿注明的例外不变：块之后才到的链接引用定义作用不到这个块。

- **顶层的围栏代码块。**
  - 开头一段，显示语言标签。
  - 每个写完的内容行一段。开 `markdown-highlight` 时，高亮结果回来后输出。
  - 结束围栏不输出。
- **顶层列表：每个顶层项一段。**
  - 下一项或下一个顶层块开始时输出。
  - 一项按单独的文档渲染。
  - 序号取列表首项的序号加项的下标，后面各项源码里写的数字不算（CommonMark 的编号规则）。
- **表格整表一段。**
- **其余顶层块各一段**：段落、标题、引用、提示块、HTML、分隔线、脚注、缩进代码。
- **间距由每段自带：**
  - 一次流的第一段为 0；
  - 顶层块之前为 1；
  - 代码块的开头和各行之间为 0；
  - 顶层列表的项之间，源码里前面有空行为 1，否则为 0。

### 2. 整篇渲染按同样的规则画列表

`Markdown` 对所有层级的列表用同一套按项的规则，取代初稿全列表统一的 `loose` 和标记宽度：

- **标记宽度按项算。** `9.` 占 3 列，`10.` 占 4 列，第 10 项起文字右移一列，接受。
- **项与项之间。** 源码里有空行为 1，否则为 0。
- **项内的子块之间。** 同样按源码里有没有空行。

### 3. 不变式

一次流的各段按顺序叠在一列里渲染，和整篇 `Markdown::new(source)` 在同宽下输出相同。这对所有成立：

- 任意的推送切法；
- 开或关匀速；
- 开或关高亮。

例外只有上面那条链接引用定义。

### 4. 尾部

`MarkdownTail` 渲染最后一段之后显示出来的文本。

- **未完的块是围栏代码块时**，等高亮的整行和末尾的半行画成 `code_block_color` 的 `Text`，不经 Markdown 解析，缩进和已输出的行相同。最多画窗口行数那么多行，多出的部分会被 ink-rs 裁掉。
- **其余情况**，同初稿：经 `settle` 和渲染器。

### 5. 后台高亮

开 `markdown-highlight` 时：

- **线程。** 每个进程一个，第一次用时启动。语法集和主题的加载、语法的编译都在这个线程里。
- **按行发送。** 流把顶层代码块写完的行按顺序发过去。线程按块延续 syntect 的状态，一行只花这一行的时间。
- **取回结果。** 结果经流自己的通道回来，在 UI 线程按顺序输出成段。
- **唤醒。** 用 `AppHandle::update` 唤醒 UI。没有待处理的工作时不持有 `AppHandle`，应用能自然结束。
- **未知语言**的块，行写完即输出，用 `code_block_color`。
- **不开这个 feature** 时没有线程，行写完即输出。
- **整篇的 `Markdown`** 保留同步高亮和按行缓存：它渲染的是写完的文本。

### 6. 模型的开销只随新数据增长

- **未完的顶层围栏代码块**只对新行找结束围栏，不重新解析。
- **其他未完的块**在一行写完时从块的开头解析，同初稿。列表从未完的项开始解析，不从列表开头。
- **匀速揭示**按推送和揭示维护积压的字素数，一次 tick 只数它揭示的部分。推送边界处跨两次推送的字素多算一个，接受。

### 7. hook、发送端和尾部组件

```rust
let stream = use_markdown_stream(cx, options, on_piece);
```

- **`stream.sender(app)`** 返回 `MarkdownSender`，`app` 是调用方给的 `AppHandle`（见第 11 条）：
  - `Clone + Send`，`push(&str)` 可在任意线程调用；
  - 同一批推送只唤醒一次；
  - `finish(self)` 消耗它；
  - 它持有这个 `AppHandle`，生产者持有期间应用不退出，文档写明。
- **`on_piece`** 在 UI 线程按顺序对每段调用一次。一段进入应用的历史和离开尾部在同一帧。定稿的段交给应用自己的 `Static`，016 的这条不变。
- **句柄还提供：**
  - 尾部组件；
  - `set_pacing`；
  - `reset`：之前的发送端推送的内容丢弃；
  - 状态栏用的计数。
- **模型**放在 hook 持有的 `Rc<RefCell>` 里，每帧不克隆。
- **时钟**只在开匀速且有积压时运行。不开匀速时，推送触发一次渲染，同一帧窗口里的推送由 ink-rs 合并。
- **`MarkdownStream`** 保留为公开的 headless 层：不用 hook、不用终端能驱动和测试，等待高亮结果不靠轮询加 sleep。

### 8. demo

`examples/markdown.rs` 改用 hook：

- 生产者是线程，按时间表 sleep 后经发送端推送，去掉 demo 自己的时钟。
- 按键和 `--fps` 不变。
- 新增 `--file PATH`，流式显示这个文件，和 `--rate BYTES`，每秒发这么多字节、每 8ms 一块。主 agent 用它们在 tmux 里压测大文件。
- 状态栏的帧率改为最近一秒实际渲染的帧数。
- 历史放在 demo 自己的存储里，经 `Static::from_fn` 按下标渲染，每帧不复制（见第 11 条）。

### 9. 测试

两个，放在 `tests/markdown.rs`：

- **段与整篇等价。**
  - 语料覆盖各类块和切点上的边界情形。
  - 切法：逐字符、每 3 字节、每 17 字节、逐行、整篇。
  - 开关匀速，宽度 80 和 40。
  - 两套 feature 下都跑。

  这是本方案的核心不变式：进了 `Static` 的段改不了，提前定稿的错误只能由这个测试发现。逐字符切法覆盖了切点。
- **hook。**
  - 线程经发送端推送 demo 的回答，最终输出等于整篇渲染。
  - 不开匀速时，流结束后推进时间没有新帧。

  它验证发送端、唤醒和同帧交接，这些单元测试覆盖不到。

### 11. Codex 报告的两个缺口

第一次派出的 Codex 读完代码后停下，没有改文件，报告 ink-rs 0.1.4 缺两个原语：

- `Static::new` 收 `Rc<[T]>`，应用的历史每增长一次要复制一份；
- `AppHandle` 没有不保活的形式，hook 的句柄若持有它，应用不能自然结束。

Claude 测了第一条：每帧克隆历史、转成 `Rc<[T]>`，2 千项 5µs，2 万项 61µs，10 万项 377µs。第二条来自 brief 规定的 `stream.sender()` 不带参数。Claude 对两条都建议不改 ink-rs，问用户。用户定：

- 「ink-rs 加 Static::from_fn」：ink-rs 加 `Static::from_fn(len, render)`，见 ink-rs 的记录 066，随 ink-rs 0.1.5 发布。0.1.5 发布前，worktree 的 `Cargo.toml` 用 `[patch.crates-io]` 指向本机的 ink-rs，集成时换成 `0.1.5` 的要求。
- 「sender 接收调用方的 AppHandle」：`stream.sender(app)`。hook 返回的句柄不持有 `AppHandle`。高亮结果要唤醒 UI 时，借进行中的工作带的句柄，结果交付后释放：
  - 发送端的推送带发送端的句柄；
  - 匀速 tick 揭示的行，带 hook 渲染时取的句柄，运行中的时钟让应用保持运行。

Codex 的会话接着做，补充的 brief 见 [markdown-stream-gaps](briefs/markdown-stream-gaps.md)。

## 备选与取舍

- **列表整块定稿。** 长列表留在尾部，300 项每帧 7.5ms，和代码块是同一个问题。
- **表格冻结列宽、逐行定稿。** 前几行定下列宽，后面更宽的行只能折行或截断，和整表渲染不一致。用户选整表。
- **代码块整块留在尾部，靠视图层缓存省高亮（初稿的做法）。** 缓存省掉高亮，省不掉布局和绘制。300 行不高亮要 4.8ms，长度没有上限。
- **代码行不等高亮就进 `Static`。** `Static` 只写一次，之后改不了颜色。
- **高亮留在 UI 线程，启动时预热语法。** 要编译所有可能出现的语言，启动变慢；编译可能落在某一帧里。
- **尾部的代码行画高亮。** 要么在 UI 线程高亮，要么多一轮往返。行在高亮回来后的下一帧进 `Static`，未高亮的颜色在尾部停留一两帧。
- **分三个 worker 先后写。** 用户选一次写完。

2. 派一个 Codex（`codex exec -s workspace-write`）：

3. 主 agent 集成：
   - review，合入；fmt、clippy 和全量测试；
   - README 和 `docs/design.md` 写 Markdown 模块；
   - 补本记录的结果，删 worktree 和分支。
4. 主 agent 压测（用户要求的「压测大数据量的场景」）：
   - 写 `examples/markdown-stress.rs`。它不经终端，逐帧计时，场景如下：
     - 5000 行代码块：Rust，以及 TypeScript 测冷启动；
     - 300 项列表、300 行表格、20 KB 段落；
     - 1 MB 的混合回答，约 2000 段；
     - 每帧到达 4 KB；
     - 匀速下积压 100 KB；
     - 列表项里含 300 行代码块。
   - 阈值（release，本机）：
     - 表格、段落和列表项里的长代码块之外，每帧 p99 ≤ 4ms，最大值 ≤ 8.33ms，含语法第一次编译；
     - 推送的总时间和输入大小成正比；
     - 表格、段落和列表项里的长代码块只报数字，记为已知限制：列表按项定稿，一项写完前留在尾部。
   - tmux 里用 demo 的 `--file`、`--rate` 跑生成的大文件，`--fps 120` 下平均不低于 115 fps。
