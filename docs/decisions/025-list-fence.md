# 列表项里的代码块按行定稿

- 日期：2026-10-22
- 状态：实施中
- 提交：无
- Brief：[list-fence](briefs/list-fence.md)

## 背景

顶层代码块每写完一行定稿一段；列表项里的代码块整项留在尾部，每帧重新解析，500 行时每帧 p50 6.52 ms、p99 14.93 ms、峰值 59.38 ms（[024](024-bingo-research.md) 的表）。编码 agent 的回答常把代码放在列表项里。调研报告的方案：

- 流模型改成递归的 `Frame` 栈：含代码块的列表项压一层，记源码的内容列、标记、标记是否画过、本层列表的序号。
- 项在代码块那一行切开：之前的文字作一段 `Document`，之后是 `Opening` 和逐行的 `Line`；代码块结束后，项的剩余部分剥掉内容列，在这一层用同一个解析器继续，其中的代码块递归处理。
- 段带上所在的标记层（`hang`），渲染时套一层和 `render::list` 同构的标记列；源码缩进和渲染缩进分开存。
- 引用里的代码块、首行是代码块的任务项、制表符缩进、内容列说不准的情况，保留整项留在尾部，等价比覆盖面要紧。

## 决策

- 用户定：
  - 「按行定稿进 0.3.0」：选按行定稿。版本号后来改为 0.2.2：用户对「eink-rs 这一版发什么版本？」选「不拆 tokio，发 0.2.2 (Recommended)」，见 024 的结果。
- Claude 按用户确认的方案（主 agent 在方案里写「嵌套深度不限」「以下三种情况维持现状，继续留在尾部」，用户选按行定稿，其余按报告的推荐）定细节：
  - 嵌套深度不限：机制相同，多一层不多一份代码。
  - 引用、首行代码块的任务项、制表符缩进留在尾部。
  - 它在 023 的 Markdown 接入之前合入：它进 0.2.2，023 在它之上 rebase。调研报告推荐 023 在前，那时 0.2.2 的范围未定。

## 备选与取舍

- **不改**：0.2.2 早发，列表项里的长代码块在 120 fps 下 102 帧超时。
- **限制尾部高度**：省 ink-rs 一侧的布局和 diff，Markdown 的解析每帧随长度增长。
- **限于顶层项**：少约 60 行，子项里的代码块留在尾部。

## 方案

一个 Codex worker（`codex exec -s workspace-write`），工作目录是 scratchpad 里基于 main 的 worktree `wt/eink-list-fence`，不提交，不改文档。brief 见 [list-fence](briefs/list-fence.md)：

- 改 `src/markdown/stream.rs`（约 +250 行）和 `piece.rs`（`hang` 的渲染，约 +60 行）；整篇渲染的 `render.rs` 不变。
- 测试：`pieces_equal_document` 覆盖等价，加 10 组语料（有序、松散、首行、子项、宽标记、两个代码块、被项结束打断、懒续行、回退路径、流在代码块中途结束）；加一个无界面测试，500 行代码块在列表项里逐行推送，每行之后尾部不超过一行加项头：等价测试看不出定稿与否。
- 验收：fmt；clippy `--all-features` 和 `--features markdown`；`--lib`；`--test markdown` 两组 feature。

主 agent 集成：review，提交，全量测试，`docs/design.md` 的「定稿」「尾部」两节，`markdown-stress` 重测 500 行列表项场景（目标接近顶层的 0.21 / 6.18 ms），在 tmux `ink-rs` 会话里看流式回答，补结果，删 worktree。之后发 0.2.2，发版开新记录。
