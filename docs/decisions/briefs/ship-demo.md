# Task: `ship`, a multi-page deploy console example for eink-rs

## Goal

It is the example that shows what eink-rs can do in one program: the Ink UI components and their themes, the CLI framework, and the in-app router with directory routes, layouts and parameters. ## Command line

```text
ship [ROUTE]...              full screen in the alternate screen, starting at ROUTE
                             (`ship`, `ship services api logs`, `ship deploy api`)
ship status [SERVICE]        print a snapshot and exit; an unknown service exits 1
ship logs <SERVICE> [-n N] [-f]
                             print the last N lines (default 20); -f keeps printing new
                             lines in the normal screen until q, Esc or Ctrl-C
ship completions <SHELL>     from eink-rs's `completion` feature
```

- `main` calls `eink_rs::cli::run_with`, turning on `alternate_screen` only when no subcommand was given. `status` and `logs` stay in the normal screen so their output remains in the terminal's scrollback.
- `logs -f` appends lines as permanent output with ink-rs `Static`. ink-rs writes only the first `Static` in the tree, so use one.
- An unknown service in `status` or `logs` ends with `AppHandle::exit_with_error`, so the process prints `Error: ...` listing the known services and exits 1.
- The root parser flattens `RouteArgs<routes::Route>` next to `#[command(subcommand)] command: Option<Command>`. `Command` is a hand-written enum with `#[derive(Subcommand, Clone, PartialEq, Commands)]`.

## Pages

Generated by `eink_rs::router::routes!("src/routes")`:

```text
src/routes/
  _layout.rs                 the shell around every page
  index.rs                   /
  services/
    index.rs                 /services
    [service]/
      _layout.rs             /services/:service header and tabs
      index.rs               /services/:service
      logs.rs                /services/:service/logs
      scale.rs               /services/:service/scale
      rollback.rs            /services/:service/rollback
  deploy/
    index.rs                 /deploy                pick a service
    [service]/
      _layout.rs             the wizard's draft and step bar
      index.rs               /deploy/:service       pick a version
      regions.rs             /deploy/:service/regions
      review.rs              /deploy/:service/review
      run.rs                 /deploy/:service/run
  settings/
    index.rs                 /settings              theme
    account.rs               /settings/account
```

- **Shell** (`_layout.rs`):
  - a header with the product name, a "simulated" label, a breadcrumb built from the current route's `Display`, and service counts by status as Badges;
  - the outlet;
  - a footer with key hints, derived by matching on the current `Route` (typed, no strings), so pages do not report their keys upward.
  - Esc goes back when `can_go_back()`, otherwise exits. Esc and ink-rs's default Ctrl-C are the only global keys; several pages take text input, so letters belong to pages.
  - It owns the theme: the selected palette lives in its state; it provides that `Palette` and a handle (current choice plus a `Callback` from `use_callback`) that the settings page uses to change it. `State` cannot be provided; see how `Router` provides a `Callback`.
  - Its own colors come from a custom component theme (`From<&Palette>`, read with `use_theme`), so they follow the palette, as in `examples/theming-custom-component.rs`.
- **`/`**: per-region health (ProgressBar plus a percentage), a sync indicator (Spinner while the simulator is syncing), the current incident (Alert, when there is one), recent deployments including running ones (UnorderedList), and a menu (Select) whose values are paths opened with `push_path`.
- **`/services`**: a filter TextInput above a list drawn from `use_select_state` (not the `Select` component), each row with name, version, replicas and a status Badge. Up/Down move, Enter pushes `/services/<name>`. Typing filters.
- **`/services/:service` layout**: reads the parameter with `use_param`; shows name, version, status Badge and replicas; tabs for overview, logs, scale and rollback switched with `replace`, so tabs do not stack history; `d` pushes `/deploy/<name>`. An unknown service renders an Alert instead of the outlet. Its state survives tab switches (the router keeps a layout shared by the old and new route); show one piece of layout state that makes this visible, such as a refresh counter or a pinned flag.
- **overview** (`index.rs`): instances as an OrderedList (id, region, status, uptime), CPU and memory ProgressBars.
- **`logs`**: a live tail sized to the window (`use_window_size`), level-colored; space pauses and resumes; a paused label.
- **`scale`**: a TextInput for the replica count (validated, 0 to 20), Enter shows a ConfirmInput, yes calls the backend and shows a StatusMessage.
- **`rollback`**: a Select of earlier releases (version, age, author); Enter asks with ConfirmInput; yes starts a deployment of that version in the backend and shows its progress on the page.
- **Deploy wizard**: `/deploy` picks a service (Select) and pushes `/deploy/<name>`. Under `[service]/`, the layout holds the draft (version, regions) and renders a step bar; version (Select), regions (MultiSelect, at least one), review (summary plus ConfirmInput), run (ProgressBar for the whole deployment, Spinner and label for the current phase, StatusMessage on success or failure). Going back keeps the draft; a draft belongs to one service, so a different service starts a fresh draft. Confirming uses `replace` to the run step, so back from run skips the review. The deployment runs in the backend: leaving the run page does not stop it, and `/` lists it.
- **`/settings`**: a Select of three palettes (Ink UI's default and two of your own); choosing one recolors every page at once. A key opens `/settings/account`.
- **`/settings/account`**: an EmailInput with domain suggestions and a PasswordInput for an API token. Tab moves focus between them through ink-rs focus (`use_focus`); each field's `is_disabled` follows its focus. Enter saves through the backend and shows a StatusMessage.

Across the app, each of `push`, `replace`, `back` and `push_path` is used where it fits; list where in the report.

## Data

- `src/backend.rs`: a `Backend` trait and its data types (services, instances, releases, regions, incidents, deployments, log lines, account). Pages and commands read and write only through it. A small context value wraps `Rc<RefCell<dyn Backend>>` with pointer equality, and a hook returns it. The root component creates the backend once and provides it.
- `src/sim.rs`: `Simulator`, the only implementation. A clock drives it: service status changes, CPU and memory move, log lines arrive, incidents open and resolve, deployments advance through phases (build, push, rollout per region). Seeded and deterministic for a given elapsed time, with its own small PRNG. One deterministic case fails a deployment, so the failure path is reachable; say which in the crate doc. Nothing outside `sim.rs` and the root names `Simulator`.
- Pages poll the backend from `use_animation` or an equivalent, not from threads.
