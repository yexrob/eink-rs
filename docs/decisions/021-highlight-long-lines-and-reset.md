# 高亮的长行上限和重置后的排队工作

- 日期：2026-10-22
- 状态：实施中
- 提交：无
- Brief：无

## 背景

[019](019-pierre-highlight-research.md) 调研 pierre 后列出四点可借鉴。用户回复：「可以 第1 2 点等你弄完手头的工作后搞一下」。

1. 长行上限。syntect 处理一行的时间随长度增长，后台线程处理一条长行时，所有流后面的行排队等它；整篇 `Markdown` 在渲染线程上高亮，长行拖慢当帧。
2. 重置后丢掉旧流排队的工作。`reset` 换掉流，旧流 `Drop` 时为未闭合的块发 `Close`；线程高亮排在 `Close` 前面的旧行，结果发给没人收的通道。

## 决策

- 用户定（上面的原话）：做第 1、2 点。
- Claude 按用户的授权定：
  - 长行上限 1000 字节，按去掉行尾换行后的长度算，超过的行用主题的默认样式整行显示。
  - 超长行不推进解析状态，下一行从它前面的状态开始高亮，和 Shiki 一致。
  - 整篇高亮和后台线程共用一个按行高亮的函数，流式输出和整篇渲染的结果保持一致。
  - 流持有一个 `Arc<()>`，每条 `Work::Line` 带它的 `Weak`；后台线程取到工作时，流被丢弃的跳过。

## 备选与取舍

- **阈值**：pierre 取 1000（UTF-16 单位），VS Code 的 `editor.maxTokenizationLineLength` 取 20000。主 agent 在本机用 release 构建量了 syntect（`regex-fancy`，预热后，单行）：

  | 内容 | 1k 字节 | 3k | 10k | 30k | 100k |
  |---|---|---|---|---|---|
  | Rust 语句 | 2.7 ms | 8.3 | 26.9 | 82.9 | 251.7 |
  | 压缩的 JS | 6.0 ms | 18.5 | 77.0 | 274.7 | 1823.3 |
  | JSON | 0.7 ms | 1.9 | 7.3 | 16.1 | 51.2 |
  | 带转义的字符串 | 1.1 ms | 3.2 | 10.8 | 32.5 | 101.0 |

  1000 字节一行不超过 6 ms，低于一帧；3000 字节的 JS 到 18 ms。取 1000。按字节算：正则的开销随字节数增长，`len()` 不用遍历。
- **超长行之后的解析状态**：
  - 保持超长行之前的状态（选用）：Shiki 的 `codeToTokensBase` 跳过超长行，`stateStack` 不变；超长行开了多行字符串或注释时，后面几行颜色会错，和 Shiki 相同。
  - 重置为初始状态：块中间的多行注释或字符串里出现长行时，后面的行颜色会错，没有好处。
  - 块的其余行不上色：颜色不会错，代价是一条长行让整块失色。
- **识别丢弃的流**：
  - `std::sync::mpsc::Sender` 不暴露接收端是否关闭，发送失败发生在工作做完之后。
  - 每块的标记不行：块闭合后，它排着的行在等结果。
  - 流在 `Drop` 里置一个原子标志：要加 `Drop` 逻辑；`Weak` 的计数随流释放归零，不用额外代码。

## 方案

主 agent 自己做，不派 worker。

- `src/markdown/highlight.rs`：抽出按行高亮的函数，带上限；`highlight()` 和后台线程共用。`Work::Line` 加 `Weak<()>`，线程取到工作时检查。
- `src/markdown/stream.rs`：流加 `Arc<()>`，提交时附上 `Weak`。
- 不加测试：上限在共用函数里，流式和整篇的一致由构造保证，现有的一致性测试覆盖调用路径；上限影响的是耗时，量过；跳过丢弃流的工作没有可观察的输出。
- 验收：`cargo fmt --check`，`cargo clippy --all-targets --features markdown-highlight -- -D warnings`，`cargo test --features markdown-highlight`，全量测试。
